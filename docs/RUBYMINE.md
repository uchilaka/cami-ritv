# Setting up your RubyMine IDE

## Configure RSpec to preset `RAILS_ENV=test` globally

> This is a requirement for using the built-in test run controls in RubyMine

- Go to the top menu and select **Run > Edit Configurations...**
- In the bottom-left corner of the dialog, click **Edit configuration templates...**
- Select your testing framework from the list on the left (e.g. RSpec, Minitest or Cucumber)
- Locate the **Environment variables** field
- Click the folder/browse icon at the end of the field or type it directly as: `RAILS_ENV=test`
- Click **OK** to apply. Any temporary test configuration generated by right-clicking a file or folder going forward will now automatically use this variable

## Installing the tracked run configurations

This repo keeps its JetBrains run configurations in `.ide-configs/`, which is tracked.
RubyMine only reads `.idea/runConfigurations/`, and `.idea/` is gitignored — so a fresh
clone or worktree starts with an empty Run menu until you install them:

```shell
bundle exec thor devkit:ide-configs
```

It copies anything not already present and leaves your local edits alone. Pass `--force`
to overwrite them with the tracked versions, and `--dry-run` to see what it would do.

**They are copied rather than symlinked, on purpose.** RubyMine rewrites a run
configuration whenever you save it, stamping in `<module name="...">` — the name of the
directory the project happens to live in. Linking `.idea/runConfigurations` at the tracked
directory would push that straight into version control, and in a worktree it would write
the worktree's folder name. The configs already carry the scars: nine say `cami`, two say
`cami-ritv`.

So your IDE's edits stay inside gitignored `.idea/`. To share one, edit the file in
`.ide-configs/` and re-run the command.

That includes `.ide-configs/Template RSpec.run.xml`, which presets the variables below —
import it rather than clicking through the dialog if you prefer.

## `RAILS_ENV=test` on its own is not enough

`RAILS_ENV` tells Rails which environment to boot. It does **not** decide which `.env` files
direnv already loaded into your shell — that is `RUBY_ENV`. So a shell sitting in
`development` hands the test run a development-flavoured environment, and RubyMine inherits
it. Two variables in particular will break the run:

| Variable | Behavior when inherited from a development shell |
| --- | --- |
| `RAILS_MASTER_KEY` | If `config/credentials/test.key` is absent, Rails uses this value instead of a key file and may fail to decrypt `test.yml.enc`; when the file exists, `config/environments/test.rb` clears the inherited value. |
| `APP_DATABASE_NAME_PRIMARY` | `config/environments/test.rb` replaces a non-`_test` value with the test database name before `spec/rails_helper.rb` checks it. |

`config/environments/test.rb` force-corrects the database *names*, but nothing corrects
`RAILS_MASTER_KEY`.

Add these to the same **Environment variables** field, alongside `RAILS_ENV=test`:

- `RAILS_MASTER_KEY=` — leave the value **empty**. Rails reads this with `.presence`
  (`active_support/encrypted_file.rb`), so an empty value falls back to
  `config/credentials/test.key`. RubyMine cannot unset an inherited variable, but it can
  blank one, which has the same effect here.
- `APP_DATABASE_NAME_PRIMARY=sails_test`
- `APP_DATABASE_NAME_CRM=twenty_crm_test`

The equivalent from a terminal, for comparison:

```shell
env -u RAILS_MASTER_KEY RAILS_ENV=test bundle exec rspec
```

## Troubleshooting

**`Could not find command "..."` from a `bundle exec thor` run.** The Thorfile calls
`require config/environment`, so any boot failure leaves Thor with zero commands loaded and
it reports the command as missing rather than showing the real error. Re-run with the
environment loaded directly to see the actual exception:

```shell
RAILS_ENV=test bundle exec ruby -e "require File.expand_path('config/environment', Dir.pwd)"
```
